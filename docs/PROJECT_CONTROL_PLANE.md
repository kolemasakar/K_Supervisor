# PROJECT_CONTROL_PLANE
Опис керуючого рівня K_Supervisor для автоматизованого життєвого циклу AI-проєктів.

Version: 0.2
Status: ACTIVE
Baseline: v0.3 Phase 5

## 1. Purpose

K_Supervisor combines two layers:

```text
AI Project Lifecycle Control Plane
+
Modular Multi-Agent Execution Core
```

The Control Plane manages projects from onboarding through provisioning, implementation, validation, release readiness, publication handoff, and maintenance.

The Multi-Agent Core executes project work through reusable agents, capabilities, workflows, tools, and providers.

## 2. Control Plane Components

The baseline Control Plane consists of:

```text
Project Factory
Project Registry
Project Scheduler
Human Intervention Broker
Notification Broker
Secret Manager
Release Manager
```

These are platform services. They are not domain-specific agents.

## 3. Project Factory

Project Factory creates and bootstraps a project from an approved ProjectSpec.

Responsibilities may include:

- repository creation or connection;
- repository bootstrap;
- baseline documentation generation;
- roadmap generation;
- initial architecture and contracts;
- initial agent/workflow scaffolding;
- CI bootstrap;
- integration planning;
- environment preparation;
- first-working-state validation.

Project Factory must use reusable templates and contracts rather than project-specific hard-coded logic.

## 4. Project Registry

Project Registry is the authoritative index of projects known to K_Supervisor.

It stores or references:

```text
project identity
project state
ProjectSpec version
repository references
active roadmap phase
integration references
environment references
release targets
current blockers
notification policy
resource policy
```

A project remains addressable independently of any individual task or chat session.

## 5. Project Scheduler

Project Scheduler coordinates concurrent work across multiple projects.

Core rule:

```text
One blocked project must not block unrelated projects.
```

The scheduler must support project-level isolation for:

- state;
- workspace;
- credentials;
- budgets;
- locks;
- agent runs;
- logs and audit records;
- rate and concurrency limits.

Global policies may restrict:

```text
max_parallel_projects
max_parallel_agent_runs
provider rate limits
compute limits
cost limits
```

## 6. Human Intervention Broker

Human Intervention Broker handles work that cannot or should not be completed autonomously.

Typical triggers include:

- account creation requiring identity verification;
- CAPTCHA;
- 2FA;
- payment or subscription approval;
- legal acceptance;
- irreversible or high-risk actions;
- credential creation that requires owner interaction;
- architecture or scope decisions requiring explicit approval;
- publication actions reserved for the owner.

The broker creates a structured HumanActionRequest instead of leaving a workflow in an ambiguous waiting state.

Baseline fields:

```text
action_request_id
project_id
reason
required_action
service
severity
blocking
deadline
resume_condition
verification_method
status
created_at
```

If the request is blocking, the affected project may enter `WAITING_FOR_OWNER` while other projects continue.

## 7. Notification Broker

Notification Broker delivers owner-facing events generated by the platform.

The initial and primary notification channel is:

```text
EMAIL
```

Email is the only notification transport required for the first implementation baseline.

Future channel adapters may include:

```text
WHATSAPP
VIBER
other messaging services
```

These future channels are architectural extension points only. They are intentionally not required for the initial implementation.

Workflows and agents must not depend directly on email, WhatsApp, Viber, or another transport. They emit platform notification events; Notification Broker applies channel policy.

## 8. Notification Events

Baseline NotificationEvent fields:

```text
notification_id
project_id
event_type
severity
title
summary
action_required
human_action_request_id
blocking
created_at
metadata
```

Typical event classes:

```text
ACTION_REQUIRED
PROJECT_BLOCKED
FIRST_WORKING_REACHED
RELEASE_READY
VALIDATION_FAILED
CRITICAL_FAILURE
OWNER_APPROVAL_REQUIRED
```

Informational technical events should normally remain in logs or digests rather than generating immediate owner email.

## 9. Email-First Delivery Policy

The initial Notification Broker must support:

- one configured owner email destination;
- structured subject and body generation;
- retryable delivery errors;
- delivery attempt audit records;
- duplicate suppression or idempotency protection;
- links or references to the affected project when available.

Notification delivery and owner action are separate concepts:

```text
NOTIFICATION_SENT != OWNER_ACTION_VERIFIED
```

When possible, K_Supervisor should verify the requested owner action automatically and resume the project without requiring a manual `done` message.

## 10. Secret Manager

Secret Manager provides references to credentials without exposing raw secrets in project documentation, repositories, AgentDescriptors, audit events, or notification messages.

Preferred logical form:

```text
secret://<scope>/<name>
```

Examples:

```text
secret://notifications/email
secret://project/PROJECT_000001/github
secret://project/PROJECT_000001/provider_x
```

The concrete secret backend remains replaceable.

## 11. Release Manager

Release Manager prepares and validates release targets.

Potential targets include:

```text
ChatGPT Plugin
GPT Store package (legacy compatibility / migration)
API service
web application
CLI/package
internal agent
other deployment targets
```

For `CHATGPT_PLUGIN`, K_Supervisor prepares portable skill/workflow assets, reference material inventory, app/connector/MCP dependencies, regression prompts and access/sharing checks. Legacy Custom Action dependencies are inventory-only until explicitly rebuilt and verified.

`GPT_STORE` remains supported for existing migration work but is not the preferred target for new ChatGPT projects.

Automatic Plugin Directory, GPT Store or other external publication is not a platform requirement. External availability is handled per project by the owner or workspace administrator when the project reaches the appropriate release-ready state.

## 12. First Working State

A project may declare a project-specific Definition of First Working State.

The default meaning is:

- core path executes successfully;
- required integrations are available or explicitly mocked;
- blocking tests pass;
- known limitations are documented;
- the system can demonstrate its primary intended function.

Reaching this state is a platform event and may trigger an owner email.

## 14. Service/API Boundary

Phase 5 adds a narrow versioned interface in front of existing Project Registry lifecycle operations.

```text
ServiceApiV1
    -> ProjectRegistry.get/list
    -> ProjectRegistry.transition_lifecycle
    -> ProjectRegistry.transition_operational
```

The Service/API boundary does not own a second state machine. Authentication/scopes and durable mutation idempotency are enforced at the service boundary, while lifecycle validity, Project snapshot mutation, transition history and audit remain owned by existing control-plane contracts.

The Phase 5 surface intentionally excludes ProjectSpec administration, Human Intervention/Approval mutation, Workflow/Runtime dispatch, release/publication actions, Tool/Provider side effects and secret resolution.

## 15. Design Boundary

The Control Plane does not replace the Multi-Agent Core.

The Control Plane manages project lifecycle and ownership boundaries.

The Multi-Agent Core performs project work through contracts, capabilities, workflows, and controlled execution.
